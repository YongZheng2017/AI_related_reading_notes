# 交互：观察与动作空间的扩展

## 模态与触发时机的扩展

- 模态决定观察和动作的形式： Agent 是只读文本，还是也能听见声音、看见屏幕、感知力矩；是只能输出 token，还是也能发声、点击、驱动关节。
- 触发时机决定观察和动作的节奏：观察是 Agent 主动去取，还是世界主动推来；动作是必须在一个回合内做完，还是可以跨越回合、中途被打断、被更紧急的事抢占。回合制是训练留下的假设，不是环境的性质。 真实环境不会等模型作出反应：邮件在它思考时到达，用户在它说到一半时插话。

&nbsp;

## 异步与事件驱动

为什么需要异步：

- 异步执行是常态——许多任务需要长时间运行，不应阻塞用户交互。
- 事件优先级的动态判断；
- 中断和恢复的流畅性——被打断的对话或任务应该能够自然恢复。

&nbsp;

LLM 的训练范式假设同步——发出工具调用后，下一条消息必须是工具结果；而真实部署却要求异步——用户随时可能打断，多个任务可能并发推进，外部事件可能在工具尚未返回时就抵达。

&nbsp;

事件驱动的异步 Agent 架构：所有的输入、输出、思考过程和外部交互都被统一建模为事件流——一条时间线上依次排列的事件记录。 

&nbsp;

OpenClaw 的事件驱动机制实现：

- 通过 Gateway 控制平面接收多渠道消息并路由到 Agent 运行时。
- Hooks（事件钩子）：响应 Agent 生命周期中的事件，如会话创建、重置等。
- Cron（定时调度器）：按 cron 表达式执行周期性任务。
- Heartbeat（心跳守护进程）：每隔 N 分钟唤醒一次 Agent，检查是否有需要关注的事项。

短板：对于内置渠道之外的第三方事件源，例如一封新邮件到达、一个外部 API 回调推送， OpenClaw 缺乏即时接入的通道， Agent 无法在事件发生后立即做出响应。
解决方案：引入 Channel 机制——在 Gateway 和 API 之间建立实时的事件通道。

&nbsp;

事件驱动架构对 Agent 框架的核心价值： 真正的“主动服务”不仅需要 Agent 能定时检查世界，更需要世界能主动通知 Agent。

&nbsp;

事件触发工具：

- 定时器（set_timer）处理依赖物理时间的事件。
- 后台任务监控（monitor_shell）处理来自异步执行的工具或命令行任务的事件。
- 外部事件通道（connect_channel）把新邮件到达、 API 回调、 IM 消息等外部事件实时推送给 Agent。

&nbsp;

用户沟通工具

- OpenClaw 用户和Agent 可以随时给对方发送消息；
- 多模态沟通能力。使用生成式 UI（Generative UI），即使用 HTML 等方式生成交互式界面，以更友好的方式向用户展示信息。
- 多渠道的用户沟通与召回。消息发送扩展到即时通讯、短信、邮件、
  电话、推送等多种渠道。 

&nbsp;

虚拟身份与隔离执行环境：

- 防止敏感信息暴露，赋予 Agent 一套独立的虚拟身份；
- 虚拟身份需要部署在隔离的执行环境中：虚拟电脑（VM/容器）和虚拟手机（Android 模拟器）。
- Agent 与虚拟环境之间的数据交换通过共享文件系统完成：以卷挂载的方式连接Agent、虚拟电脑和虚拟手机，数据以文件路径引用传递而非内容拷贝，避免占用上下文窗口。

&nbsp;

事件处理机制：

- 事件循环（event loop）：事件只在每轮循环的边界被消费。当 LLM 正在推理、工具正在执行时，新到达的事件不会凭空插入、打乱当前这一步，而是先在队列中等待，待本轮到达一个安全点（一段推理结束、一次工具返回）再统一处理。取消也遵循同样的纪律。
- 事件的结构化建模：来源（谁）、渠道（方式）、内容（什么）、上下文（背景）。
- 基于紧急度的动态处理策略。
  - 取消式处理（Cancellation-Based） 用于紧急事件，其本质是为紧急事件提前制造一个安全点：主动中断当前步骤，把这一刻变成可以消费新事件的边界。
  - 队列式处理（Queued） 用于常规事件。将事件放入队列末尾，不打断当前操作。
  - 并行处理（Parallel） 用于独立的轻量级查询。在一个并行的推理会话中独立执行，调用必要的工具生成响应后立即返回。

## 语音

交互时序：

- 级联：VAD → ASR → LLM → TTS。
  - 基于串行流水线： VAD 判断用户何时说完， ASR 把音频转成文字， LLM
    理解并生成回复， TTS 再把文字念出来。
  - 问题：延迟累积，必须等待一段静音才能确认说完；信息丢失，无法表达犹豫、情绪、附和和环境声；上下文被切断，邮箱、人名和专有名词可能被分片识别而出错。
- 端到端 Omni：原生音频输入输出，按轮次交互。
- 全双工：原生音频输入输出，持续听、说和决策。

&nbsp;

实时交互：前台模型要在用户仍然在线时回应，后台模型则可以花更多时间思考。

- 方案一：快思考回应，慢思考回答。快思考可以在几百毫秒内先给出即时回应，慢思考则在后台完成更深的推导。
- 方案二：快思考交互，慢思考提醒。让后台模型通过状态栏或专门接口向前台模型提供建议，前台继续维持话头并决定如何表达。
- 方案三：端到端思考与表达统一。把思考能力直接内化到端到端音频模型中。

## 机器人操作

VLA：Vision-Language-Action 的缩写。“视觉—语言—动作模型”。它接收当前画面和一条技能指令，然后输出机器人接下来要执行的动作。
VLA 的局限：

1. 训练数据有限；

2. 只学会模仿，不一定懂后果：不知道这个动作会造成什么结果。

3. 机器人各不相同：同一个动作不一定能直接搬到另一台机器人上。

4. 观察可能过时：动作块开始执行后，物体可能被移动、遮挡或碰倒，但模型仍在依据上一帧画面做决定。

还需要另一类模型帮助判断“做了之后可能发生什么”。

&nbsp;

世界模型：在当前状态下采取某个动作，下一刻的状态可能怎样变化。
一个能用于机器人的世界模型至少要做好三件事：

1. 看懂当前状态；

2. 预测不同动作可能带来的结果；

3. 把这些预测交给规划器或控制器，帮助它们做选择。
