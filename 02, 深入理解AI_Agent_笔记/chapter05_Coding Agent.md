# Coding Agent

以开放任务为目标的通用 Agent，其核心是一个 Coding Agent 加上文件系统。因为它不只是一个工具，而是一种元能力：能在运行时动态创造出新的工具和能力。

代码对 Agent 的价值体现在两个层面。 思考上，形式化代码让思考高度严谨；表达上，一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供客观的对错标准。

&nbsp;

## Coding 是 Agent 的基础能力

代码生成不是少数专门化 Agent 的专利，而是每个通用 Agent 都该具备的基础能力。
一个基础的 Coding Agent 需配备以下七个核心工具：

1. Code Interpreter（代码解释器）

2. Bash Shell（命令行终端）

3. 读文件工具

4. 写文件工具

5. 编辑文件工具

6. 搜索文件名工具（Glob） 

7. 搜索文件内容工具（Grep）

&nbsp;

## Coding Agent 的整体流程

1. 项目文档化：先建立对整个项目的认知框架。
   a. 知识的显式化是高效协作的前提。、
   b. 项目指令文件：CLAUDE.md、 AGENTS.md。在每次会话开始时被自动注入上下文，相当于项目级的系统提示词。

2. 任务理解与需求澄清：通过探索性调研来澄清边界，必要时主动与用户对话。

3. 编写设计文档；

4. 代码实现与测试；
   a. 为新增或修改的功能编写测试用例，覆盖正常路径、边界条件和异常情况。
   b. 代码审查：Agent 对自己生成的代码进行批判性审视——可读性如何，是否有足够注释；是否存在潜在的性能问题或安全漏洞；是否遵循项目的代码风格和最佳实践。可通过阅读代码、运行 lint 工具或调用专门的代码审查子 Agent（Sub-Agent）来实现。

5. 文档同步与交付；

软件工程的核心原则：计划先于行动，验证贯穿始终，文档与代码共同演化。

## Harness 工程在 Coding Agent 中的实践

可迁移的设计原则：

1. 约束优先于指导：能用代码强制的规则就不要用文档建议。

2. 验证要自动化：测试套件、代码质量检查、行为监控。

3. 反馈越快越好，越结构化越好：错误信息越详细、越接近错误发生的时刻， Agent 的纠正效率越高。

4. 回退要可靠： Agent 在安全网内操作才能大胆试错。 Git 分支、沙盒环境、快照机制确保任何错误都可逆。

约束的另一层目的：防止过程性错误。 防止删库，删正常代码、删除生产数据、覆盖未读文件。
工具编排：故障边界控制。一个工具失败时，哪些调用应当中止、哪些应当继续？原则是故障只在同一批并行调用内传播，不上升到父级操作。

## 故障与错误恢复

四层故障：

- API 层：限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断。
- 工具层：幻觉调用（调用了不存在的工具）、参数畸形（不符合工具的输入约束）、执行抛异常，工具反复返回同一个错误，而模型不加改变地反复重试。
- 上下文层：上下文窗口溢出、压缩失败、轨迹结构损坏（如工具调用缺少配对的结果消息）。
- 控制流层：死循环（反复执行相同操作却毫无进展）与死亡螺旋（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应）。

&nbsp;

错误恢复：

1. 检测：先分类，再计数。 
   a. 捕获故障后的第一个判断不是“要不要重试”，而是“值不值得重试”。
   b. 单次错误之外，还要检测模式。一是重复调用指纹：对“工具名 + 参数”计算指纹，相同指纹反复出现就是无进展循环的明确信号；二是连续失败计数。
   c. 还有一类故障不表现为错误，需要专门的活性与完整性监控：超时后主动杀死挂起的流并触发重试。每个长连接都需要活性信号，而非仅依赖连接
   超时。

2. 恢复：分级升级，逐级透明。 
   a. 按对用户透明的程度分级，能用低级别解决就不升级：
   
     i. 静默重试。可重试错误的默认动作。指数退避叠加随机抖动；区分前台与后台调用——主循环的请求失败要重试，标题生成、输入建议这类辅助性后台调用失败则直接放弃。
     ii. 降级与接续。重试无效时，改变请求本身再试。
     iii. 暴露给用户。所有自动手段用尽后才呈现错误，并附上已经尝试过的恢复动作。
   
   b. 工具层错误：不终止会话，把错误变成模型的输入。由模型在下一轮自行纠正。
   c. 核心原则是： 错误处理的边界不是单次请求，而是整个恢复循环。在确认无法恢复之前，中间错误不应暴露给消费者——无论是用户还是订阅事件的下游系统：恢复期间扣留错误消息，恢复成功则消费者毫无感知，所
   有恢复手段均失败后才统一呈现错误。

3. 终止：每条恢复路径都要有上限。 
   a. 每条恢复路径都必须有明确的熔断上限。
   b. 死亡螺旋：错误处理路径中的逻辑本身又调用 LLM，再次出错，引发连锁反应。防护措施：
   
     i. 在错误路径上禁用一切会再次调用模型的副作用逻辑；
     ii. 用递归深度
   计数器检测并打断残余的连锁；
     iii. 在所有自动化机制之上还需要全局的终止与升级条件：最大迭代轮数、会话
   预算上限，以及连续失败超过阈值时升级到人工干预。

4. 预算上限，以及连续失败超过阈值时升级到人工干预。

## Coding Agent 的实现技巧

- 并行工具调用、流式执行与级联中止。
- 上下文的精细化管理。
  - 在文件读取层面， Agent 不应总是读取文件全部内容。对大型文件，工具应支持按行号范围读取特定片段。返回内容时附加行号标注，每行代码都以实际行号作为前缀。
  - 长输出截断与持久化处理。
- 环境信息的动态注入。每次推理前应在上下文末尾以 Agent 状态栏形式注入以下关键环境信息：
  - 当前工作目录
  - git 分支
  - 最近提交记录
  - 未暂存和已暂存的变更概览
- 命令执行环境的状态持久化。维护一个持久化的终端会话，在 Agent 启动时创建并在整个交互过程中保持活跃。每次命令都在这个共享终端中执行，保留工作目录、环境变量和会话状态。
- 即时的语法反馈机制。文件写入操作一完成，工具层就自动运行相应的 linter 或语法检查器，将检查结果作为工具返回值的一部分呈现给 Agent。如果检测到语法错误， Agent 在下一轮推理中立即看到详细错误信息。

## Coding Agent 中的搜索工具

- 正则表达式内容匹配（grep/ripgrep）：最传统的搜索方式，逐行扫描文件内容进行模式匹配。
- 文件名模式匹配（glob）：在文件系统的路径结构中查找符合模式的文件。
- 语义代码搜索：为语义搜索建立嵌入索引，试图理解查询和代码的“意义”。
- 符号级定义与引用查找：类似 IDE 的“跳转到定义”“查找所有引用”能力，能区分同名符号的定义和调用。

&nbsp;

## Coding Agent 中的文件编辑工具

文件编辑的难点不在于操作本身，而在于如何让 LLM 以高效又可靠的方式告诉系统“改哪里、怎么改”。 

- 差异描述 + Apply Model：模型不是直接指定如何编辑文件，而是生成一份变更描述——可以是类似 git diff 的差异文本，也可以是带省略标记的代码骨架（用
  “此处保持不变”之类的注释跳过未修改部分）。这份描述随后交给专门的“应用模型”（Apply Model）——通常是另一个更小、更快的 LLM——负责与原文件合并、产出完整的新文件。
- 旧字符串到新字符串（Old String → New String）： Claude Code、 Codex 和今天 Cursor 采用的方案。模型提供 old string（要被替换的原文）和 new string（替换后的新文本），框架执行简单的字符串查找替换。
- 行号定位（Old Line Numbers → New String）：模型指定“删除第 X 到 Y 行，插入新内容”。只要读文件工具提供了行号信息，模型就可以精确地看到欲删除内容的行号。
- 类 Vim 编辑命令：借鉴 Vim 编辑器的命令体系，支持复制、剪切、粘贴等丰富操作。
- 字符串首尾匹配（Old String Start + End → New String）：可以看作旧字符串替换方案的改进。模型不需要输出完整的 old string，只需提供要删除内容的开头几行和结尾几行，中间部分可省略。

## Coding Agent 的安全

致命风险要素：

- 访问私有数据
- 暴露于不受信任内容
- 具备外部通信能力
- 持久记忆

&nbsp;

Coding Agent 特别需要注意：

- 命令语义解析——Shell 命令的组合爆炸使关键字黑名单形同虚设，必须在语义层理解命令的真实效果.
- 沙盒隔离与网络出口控制
- 持久记忆的跨会话防线

&nbsp;

隔离兜底：代码执行沙盒的工程选型。

- 网络出口控制。默认断网，按需通过白名单代理放行有限目的地（包管理源、文档站点、任务明确需要的 API）。
- 文件系统隔离范围。源码目录以只读方式挂载，单独的可写工作区目录承载生成物和中间文件；凭证类文件（~/.ssh、密钥、 token）根本不挂载进沙盒。
- 资源限额与超时。 CPU、内存、磁盘配额加超时，防御死循环、 fork 炸弹（通过疯狂自我复制进程拖垮系统）和无限写盘。超时和超限应向 Agent 返回结构化错误而非静默杀死进程，让 Agent 有机会在下一轮修正策略。

&nbsp;

安全：语义解析而非关键字黑名单。

- Shell 命令安全校验：简单的关键字黑名单无法应对 Shell 的组合爆炸，生产级 Harness 采用语义解析。

&nbsp;

Agent 为谁效忠：多方委托下的忠诚度。

- 把主人的私密信息直接抖给对手，被反复施压几轮就缴械让步；
- 提示注入本质上就是一次策反，Harness 层要明确限定“忠诚对象”：主人的指令优先级最高，一切来自外部交互方的内容都默认降格为“可参考、但不具备指令效力”的数据。
- 用 Harness 为模型补上一条它默认没有的立场： 对主人绝对忠诚，对外部交互方保持审慎

&nbsp;

## 代码：通用 Agent 的元能力

- 代码作为思考工具：让 LLM 负责理解用户的自然语言问题，识别其中的数学或逻辑结构，并转化为形式化语言（如 Python）；然后交给专门的符号计算引擎或约束求解器执行，获得精确结果。
- 代码作为业务规则的约束：Harness 的核心原则之一是“约束：编码化而非文档化”——将规则从自然语言文档转化为可执行的代码，使其成为系统行为的强制约束而非建议性指南。系统提示词包含自然语言规则供理解和沟通，关键决策点配备代码化校验工具作为“守门员”确保合规性。    
  - (1) 系统提示词的自然语言规则帮助理解和解释；
  - (2) 工具描述与参数设计作为 checklist，引导模型在调用前显式核对条件； 
  - (3) 服务端基于数据库真值的代码化校验作为最后守门员。
- 代码驱动的多媒体生成。通过代码生成PPT，进行视频编辑。
- 代码作为系统适配器；
- 代码作为生成式 UI；
- 代码创造代码： Agent 自举
