# Agent评估

一个关键认识是： 评估的对象不应只是模型，而应是模型与 Harness 的组合体。

模型替换实验（model swap） ——固定 Harness，只更换更强/更弱的模型，观察分数变化幅度；如果换强模型分数不涨，说明瓶颈在 Harness；如果换弱模型分数大跌、分数随模型能力大幅波动，最直接的解读就是瓶颈在模型能力本身、当前表现主要由模型决定。

核心理念是： 评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。

&nbsp;

## 一个具体的评估示例

Rubric 评分：

1. 操作正确性

2. 政策合规性

3. 信息完整性

4. 幻觉检测（一票否决项）

评估的基本骨架：定义测试用例、运行 Agent、用 Rubric 评分、分析结果。

&nbsp;

## 评估指标体系

用 Pass@k 看能力上限：

- 在同一任务上运行 𝑘 次，只要至少有一次通过，任务就算通过；
- 如果输出是连续得分，则取最好的一次，记为 Best@k。
- 通常不是“每次都做对”，而是把探索预算拉长后终于出现一条突破性轨迹。

&nbsp;

业务可靠性：关注 Pass^k

- Pass^k（可以读作 Pass consecutive k）：同一任务连续运行 𝑘 次，要求每一次都通过，且不能触发安全、合规或幻觉等一票否决项。

- 回答的是“Agent 能否稳定可靠地交付”，而不是“能否偶尔创造奇迹”。

- 评估报告必须写清 𝑘 次尝试的口径：是同一任务的 𝑘 次独立采样，还是生产流水线上连续 𝑘 个任务。对于会产生副作用的操作，不能简单地“重试直到成功”，而应在沙盒或可回滚环境中采样，并把每一次失败都记入可靠性指标。

&nbsp;

过程指标：从黑盒到白盒

- 行动合法率：测量操作中有效且合法的比例——无效操作包括调用不存在的工具、传递错误的参数类型；越权操作指超出权限范围的行为。
- 工具调用正确率：进一步要求参数在语义上合理：搜索工具的查询词应准确表达需求，文件操作的路径应指向正确目标。
- 路径效率：衡量完成任务的经济性：步数（思考-行动-观察循环次数）、冗余动作、回退次数。
- 检索覆盖率：针对信息收集类任务，是否充分探索了信息空间。
- 成本与延迟：请求次数、 Token 花费、耗费时间。

&nbsp;

安全与合规指标：

- 触发敏感操作、数据外泄、违规内容，都应遵循零容忍原则。一次严重安全违规即否决整体评价。

&nbsp;

鲁棒性：

- 随机种子敏感性（不同初始化下表现差异有多大）
- 页面变化适应性（网站 UI 更新不应导致完全失效）
- API 抖动容忍度（能否优雅处理临时故障、超时、格式变化）
- 长时记忆干扰（上下文中积累的过时信息是否会导致错误决策）

&nbsp;

轨迹覆盖：

- 执行轨迹与最终结果的双重覆盖。既要验证Agent执行过程的轨迹，又要验证最终结果。

&nbsp;

定期人工抽检：覆盖不同任务类型、成功/失败案例和边界分数附近的模糊案例，不仅验证结果，还要审查评分理由的合理性。

&nbsp;

对抗式评审：过红队（Red Teaming）主动构造挑战性案例：表面完美但含隐蔽错误的回答、通过关键词堆砌蒙混过关的回答、利用评判模型已知偏见获取不应得高分的回答。

&nbsp;

## 自动评估环境

评估环境的基本组成：

- 数据集（Dataset）： 定义任务集合，包含初始状态、目标描述和可选的参考解决方案。
- 环境状态（Environment State）： 维护任务执行中的可变信息，需在真实性和可控性之间取得平衡。每次测试可重置到相同初始状态。
- 工具接口（Tools）： 定义 Agent 可执行的操作集合。
- 评分标准（Rubric，评分准则）： 量化 Agent 的表现。
- 执行协议（Interaction Protocol）：规定交互模式和终止条件。

&nbsp;

工具调用型评估环境：
Verifiers框架：Agent 通过调用预定义工具完成任务，验证基于可执行标准，不依赖人类标注或模型评判。
https://github.com/PrimeIntellect-ai/verifiers

&nbsp;

人机交互型评估环境：
关键设计原则：

- 渐进式信息透露（Progressive Information Disclosure）。绝不能一开始就把模拟用户的所有信息暴露给 Agent，Agent 需要通过主动提问来澄清需求，这
  个过程本身就是能力的重要体现。

&nbsp;

τ-bench：

- 用户模拟（User Simulation）。用另一个 LLM 扮演用户角色，根据预定义的指令与 Agent对话。 
- 用户模拟器遵循一个固定的脚本（已知信息 + 透露规则），确保评估可复现，同时模拟真实用户的渐进式表达方式。
- 模拟用户往往还会设置有限的耐心，如果 Agent 沟通效率低下，模拟用户就可以终止对话，导致任务失败。
- 二元奖励——所有检查全部通过才得 1 分，任何一项不通过就是 0 分。

&nbsp;

τ²-bench：

- 双控环境（Dual-Control）：不再只有 Agent 一方能调用工具，用户模拟器也能操作同一个共享环境。
- 更精确的任务规范与组合式任务生成：成功条件的歧义更少、具体任务实例可以参数化批量生成。

&nbsp;

## 评估任务数据集设计

常用评估基准：

1. GAIA

2. AndroidWorld

3. SWE-Bench Verified （Software Engineering Benchmark，软件工程基准测试）

4. τ-bench

5. τ²-bench

6. Terminal-Bench

7. OSWorld

8. OSWorld-Verified

&nbsp;

核心挑战：

- 明确性与开放性的张力：任务描述必须足够明确以确保评估可复现，又不能过于死板，以免限制 Agent的创造性。 
- 真实性与可控性的平衡。 真实任务包含不确定性和噪声，有助于检验鲁棒性，但也会影响可复现性。
- 多样性与系统性的协调。 有效的数据集需覆盖典型情况、边界条件和错误陷阱，同时还要采用有系统的组织方式，使评估结果能诊断出具体的能力短板。 
- 评估成本与覆盖范围。 数据集的规模需要在全面性与经济性之间平衡。 
- 数据泄漏（Data Contamination）防范。当评估数据被纳入训练数据时，评估测的就是记忆力而非泛化能力。

&nbsp;

任务描述的精确性设计：

- GAIA 通过明确的信息源约束、时间范围、主题和查询目标来确保答案的唯一性。
- τ²-bench 引入了情境化设计，每个任务包含多层信息：表面问题（“移动数据无法工作”）、性能期望（“绝对想要出色速度”）、约束条件（“不接受其他速度”）以及隐含情绪。
- SWE-Bench Verified 包含问题描述、复现步骤、预期/实际行为等结构化字段，标注者会验证描述与测试用例的匹配性。 
- AndroidWorld 采用参数化模板设计。一个任务不是静态文本，而是可动态实例化的模板，每次评估时随机生成不同的参数值。
- OSWorld 的任务往往不从“干净的”初始状态开始，而是从精心配置的中间状态启动，更贴近真实使用场景。

&nbsp;

任务复杂度的层次化设计：

- GAIA 设计了三级难度： Level 1 只需 1-2 个工具，Level 2 需要多步思考，Level 3 需要复杂组合。
- τ²-bench 通过业务复杂度分层：从简单的信息查询，到多步流程，再到故障诊断，最后到策略判断。
- Terminal-Bench 通过技术领域 × 操作复杂度双维度分层。

&nbsp;

可验证性与客观性保障：

- GAIA 的答案简洁明确，严格的格式规定使验证可以通过精确的字符串匹配来完成，二元结果（匹配或不匹配）确保客观可复现。
- SWE-Bench Verified 根据代码的可执行性进行验证，区分 FAIL_TO_PASS（修复前失败、修复后通过，证明问题被解决了）和 PASS_TO_PASS（修复前后都通过，证明没有引入新的 bug），实现双重验证。
- τ²-bench 的验证体系包含多层检查（各层检查结果在任务层面仍汇总为二元奖励，全部通过才算成功）：数据库状态、对话内容关键词搜索、流程合规性。
- OSWorld 配备了 134 个独立评估函数，拥有完整的 OS 访问权限，能深入检查文件系统结构、进程状态、网络连接、应用内部状态。
- Terminal-Bench 基于 Docker 容器标准化环境，结合文件系统状态检查和程序执行功能验证，canary GUID 使泄漏可追踪。

&nbsp;

任务分布的系统性设计：需要系统性地覆盖能力维度、难度维度、场景维度和边界情况。 

&nbsp;

数据质量控制与迭代改进：人工评估、持续迭代。
评估集本身的题目，必须与训练数据严格隔离。可以复用的只是环境的构造机制。

&nbsp;

## 自动化评估方法

LLM-as-a-Judge：自动化评估的核心。
Rubric（评分标准）： LLM 评判的依据。

&nbsp;

Rubric 四准则（Scale AI，“Rubrics as Rewards”）：

1. 基于专家指导——必须反映领域知识，捕捉核心事实和推理步骤。

2. 全面覆盖：涵盖事实准确性、逻辑连贯性、完整性、安全性，而且不仅定义正面标准，还要明确陷阱（Pitfall，即高风险的常见错误）。

3. 按重要性加权：分为必要项（Essential）、重要项、可选项、陷阱项。支持一票否决机制（Veto）。

4. 评价标准自包含：每个评价项独立可操作，不依赖评价者的领域知识。

&nbsp;

关键实践：

- 为每个维度定义客观可验证的评分档次，提供具体示例和边界案例帮助区分模糊情况。
- 要主动防范奖励作弊（Reward Hacking，即 Agent 找到了获取高分的“捷径”却没有真正完成任务），明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。 
- 不断迭代：通过试用收集评价者的分歧并逐步完善，最终从抽象准则演化为详尽的判例集。

&nbsp;

失败归因：从整条轨迹定位首个错误

- 必须对每条失败轨迹进行失败归因（failure attribution）：标出主要错误类别、首次出现不可接受行为的步骤、对应的工具调用或模型输出，并附上可复核的证据。
- 归因标注Agent 可以利用 LLM 规模化完成大量生产轨迹的根因分析，但不能只输出一句“失败原因”。 归因记录需要结构化。

&nbsp;

把修复目标写成可重复执行的测试用例，即回归任务（regression task）：

- 端到端回归任务：从初始状态和用户请求开始，让 Agent 完成整个任务，并检查最终状态、必要输出和安全条件。
- 轨迹前缀回归任务：把已有的上下文、对话、工具返回和环境状态冻结下来，只要求 Agent 思考并执行下一步或下几步可观察动作，成本更低，也能隔离单个策略或工具问题。
- 失败归因完成后，就可以构造包括端到端和轨迹前缀回归任务在内的评估数据集。

&nbsp;

同源模型问题：当 Agent 与评判模型来自同一家族时， Agent 可能学会利用评判模型的偏好和盲点。
多源异构评判：使用不同模型家族的多个 LLM 分别评判，使用相同的 Rubric 确保大家评判的是同一目标，通过加权平均或一致性检查聚合结果。
