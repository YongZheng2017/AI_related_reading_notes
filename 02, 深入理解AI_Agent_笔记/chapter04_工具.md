# 工具

## 工具的分类

1. 感知工具：Agent主动获取信息、感知世界的方式。例如，网络搜索工具、内部知识库检索工具。设计关键在于控制输出信息量，防止上下文爆炸。

2. 执行工具：Agent改变外部世界的方式。例如，命令行工具、代码解释器工具。执行工具的错误代价可能极高，安全约束是其设计的核心。

3. 协作工具：Agent 与其他 Agent 及人类协作的方式。例如，创建子 Agent、给子 Agent 发送消息。

4. 用户沟通工具：Agent 主动向用户传递信息的方式。例如，回复用户消息。

5. 事件触发工具：外部世界驱动 Agent 行动的方式。例如，设置定时器。注册时由 Agent 主动调用工具，

6. 声明自己关心什么事件； 触发时由外部事件异步回调，唤醒 Agent 开始处理。

## 工具设计的通用原则

能力表达形式：

1. 专用代码工具：结构化的函数调用，确定性高、可测试，但每个工具会占据数百个 token。

2. Skill + 通用执行器：用自然语言编写的 Skill 文档来描述操作流程。

&nbsp;
选择哪种形态取决于三个维度：

1. 参数复杂度：涉及嵌套对象、多字段联合校验、复杂类型约束的操作，专用工具的结构化 schema 能更好地引导模型正确传参；

2. 变更频率：频繁变化的能力用 Skill 来维护，成本远低于专用工具；

3. 模型能力： SOTA 模型可以用 Skill + 通用执行器的方式表达更多能力、减少工具数量；较弱的模型则需要结构化的工具 schema 来引导正确调用。

&nbsp;

工具粒度的权衡：

- 粒度过细会导致工具数量激增，增加 LLM 的选择负担；粒度过粗又会使单
  个工具过于复杂。
- 判断是否应该整合的核心标准是功能相似性和使用场景的重叠度。
- 当功能虽然相似但参数集差异很大、或者某个功能的使用频率极高时，保持独立反而更合理。

&nbsp;

工具的通用性设计：

- 通用工具优于专用工具，除非存在明确的安全、权限或性能理由。
- LLM 本身具有强大的思考和代码生成能力，我们应该利用这种能力而不是限制它。
- 对于需要特殊权限、复杂配置或有安全风险的操作，封装良好的专用工具仍然是必要的。

&nbsp;

工具描述：

- 核心是让 LLM 知道“什么时候用”，而不只是“能做什么”。
- 清晰列出工具的边界条件——做不到什么、不接受什么输入——往往比描述能力本身更重要。
- 参数描述应该用具体例子代替抽象规范。
- 返回值格式也需要描述清楚。
- 为每个工具附带 1-5 个真实的调用示例。 
- 当 Agent 频繁选错工具时，应优先检查工具描述而不是怀疑模型能力。

&nbsp;

参数传递：

- 一种比功能缺失更隐蔽的反模式是静默输入转换（例如中英文引号转换）——工具在执行前悄悄地“修正”模型的输入参数，导致实际操
  作偏离了模型的意图。
- 静默参数注入——工具在模型不知情的情况下向命令追加额外的参数。
- 工具设计原则： 模型感知到的世界与工具操作的世界之间，不能存在系统性的
  偏差。工具的参数传递必须保持透明，不得在模型不知情的情况下修改输入或输出。

&nbsp;

工具设计的演进：

- 第一代是直接的 API 封装。
- 第二代是 ACI（Agent-Computer Interface）原则——工具应该对应 Agent 的目标而非底层的 API
  操作。
- 第三代在单个工具的设计之上，进一步优化工具被调用、串联和发现的方式。

## MCP

Model Context Protocol（MCP） 是 Anthropic 于 2024 年底发布的开放标准，旨在统一 AI 模型与外部工具、数据源之间的通信协议。
采用客户端-服务器架构： MCP 服务器暴露一组工具， MCP 客户端（通常是 Agent 框架或 IDE）通过标准化协议与服务器通信。关键的设计决策包括：

- 标准化的工具描述格式：每个工具通过 JSON Schema 定义输入参数的类型、约束和描述，确保不同的客户端都能正确理解工具的使用方式。
- 传输层的灵活性：持本地和远程两种部署方式，本地传输采用 stdio（标准输入输出），远程传输采用 Streamable HTTP。
- 资源与工具的分离：除了可执行的工具， MCP 还定义了只读的资源（如文件内容、数据库记录），客户端可以
  浏览和读取资源而无需调用工具。以及提示模板（prompts）。

&nbsp;

三个挑战：

1. MCP 的局限性：跨会话、多事件源、离线唤醒的事件驱动架构仍需要在协议之上另行构建。

2. 上下文开销：
   a. 后端可以保留 MCP 的生态兼容性，前端仍应以 CLI +
   Skills 或代理工具实现渐进式披露，避免服务器越接越多时上下文和 token 开销同步膨胀。
   b. 层次化组织与动态工具发现。
   c. 从 MCP 到 Skills：解决工具过多的问题。 

3. MCP 的信任模型与安全风险：
   a. 工具描述投毒（提示注入）
   b. 恶意或被劫持的服务器
   c. 同名工具遮蔽（tool shadowing）
   d. 凭证管理风险

&nbsp;

安全防护：

1. 接入前审查工具描述

2. 锁定服务器版本，拒绝静默更新，升级时重新审查。

3. 为每个服务器配置最小权限的凭证。

## 感知工具

感知工具其特有的设计问题：

- 返回信息量远超 Agent 处理能力的挑战。通用做法是在工具层面集成上下文感知压缩。
- 搜索类工具的返回格式与分页：返回值应该是结构化的候选列表，数量较多时，应提供分页或游标（cursor）参数。
- 读取类工具的 offset/limit 与截断策略：read 类工具应支持 offset/limit 参数，按需读取大文件的指定片段。当内容超过阈值必须截断时，应明确标示截断情况。
- 只读性带来的工程红利：结果可以安全地缓存；多个感知工具调用可以放心地并行执行。

&nbsp;

多模态感知：

- 原生多模态处理：模型原生支持多模态
- 提取为文本：将多模态内容提取为文本。代价是信息损失：所有版式、图表、图像信息都在提取过程中被丢弃。
- 工具化多模态分析：将多模态分析作为工具。工具接受一个多模态文件和一个自然语言问题作为参数，返回自然语言描述的分析结果，工具内部可以使用多模态模型实现。

&nbsp;

## 执行工具

执行工具的错误代价可能极高，设计需要在能力开放和安全约束之间取得微妙的平衡。

- 安全机制的层次化设计：应构建多层防护体系。
  a. 第一层是输入验证：在执行任何操作之前，检查所有参数的合法性。发现异常输入时立即拒绝，不尝试“智能”修正。
  b. 权限控制：文件操作限制为只能访问特定的工作目录，命令执行维护一份禁止命令的黑名单，外部 API 检查配额和速率限制。
  c. 提议者-审核者：独立模型的安全审查。对于不可逆的关键操作，通过“提议者-审核者（Proposer-Reviewer）范式"执行更智能的审查机制。
  
      i. 事前审批：在工具执行前， 一个模型负责提议行动（Proposer），另一个独立的模型负责审查并
  批准（Reviewer）。
  
          1. 模型选择：提议模型和审批模型应来自不同的家族，理想配对是能力相近但训练偏好不同的两个模型。
          2. 在提示词设计上，两个模型的底层规则和约束必须完全一致，上下文也需要一致，
  但关注点应有所差异。
          3. 审批失败后不应简单重试，而应将拒绝理由作为工具调用结果加入 Agent 的轨迹。
  
      ii. 事后验证：在操作完成后，由审核视角检验结果的正确性。
  
  d. Sidecar 机制：与主思考并行的安全校验。Sidecar 是一种伴随主 Agent 思考循环运行的轻量级 LLM 调用模式，它不审查主 Agent 的最终输出，而是对主 Agent 的行为做独立判断。
  e. 让安全检查在用户体验层面“隐形”。安全性不以牺牲用户体验为代价。

- 自动验证与反馈闭环。如果操作结果可以被验证，就应该自动验证。

- 长输出的截断与持久化。当检测到输出超过阈值时，工具只将头尾各若干行写入上下文，完整结果则保存到临时文件。

- 执行环境的隔离与沙盒：理想的实现方式是在沙盒环境中运行，与宿主机隔离。

- 工具执行的可观测性：用于监控、审计和调试 Agent 的执行行为。提供：详细的日志、审计追踪、性能指标、以及告警机制。

- 幂等性与取消语义。
  
  - 当一次调用被取消或超时时，它的副作用到底发生了没有？ 
  - 幂等性：同一个操作执行一次和执行多次，对外部世界的影响完全相同，因而可以安全重试。
  - 采用 “预检-确认”两段式：第一段使用一个来自不同模型家族的模型和专用安全检查提示词做校验，第二段才真正执行。

## 协作工具

子 Agent 的设计哲学：核心价值在于专业化分工——与其构建一个“全能”的 Agent，不如构建一组各自专精的 Agent，让它们通过协作来解决问题。每个子 Agent 可以独立优化提示词、工具集和知识库，无需担心相互之间的冲突。

&nbsp;

子 Agent 提示词的关键要素：

- 角色定义要清晰
- 上下文来源要明确标注
- 任务边界要明确界定
- 输出格式要标准化

&nbsp;

Agent 间的协作机制：协作工具的接口可以归纳为三组原语。 其一，启动与取消；其二，消息传递；其三，发现。

&nbsp;

协作形态： 

- 同步调用（等待子 Agent 返回，适合快速完成的任务） 
- 异步调用
  （立即获得任务 ID，完成时通过事件通知）
- 流式协作（子 Agent 持续发送增量消息，适合过程本身有价值的场景）
- 多轮交互（子 Agent 主动询问、主 Agent 应答的对话式协作）

&nbsp;

人工介入：

- 超时和降级策略：需要设置超时阈值和默认行为：“如果 5 分钟内没有响应，采用保守策略”。还需要引入优先级队列：“紧急请求通过多渠道通知，普通请求只发邮件”。
- 反馈循环的建立：可归纳的判断原则可以进入知识库或 Skill，高维而隐式的偏好则可以形成后训练数据。

&nbsp;

## 主动工具发现

从被动选择到主动发现：在执行过程中意识到能力缺口时，主动用自然语言声明“我需要什么能力”，系统再动态匹配并注入。

工程上更常见的等价方案，是在系统提示词里只保留少数基础工具（web search、 code interpreter）外加一个“工具搜索工具”， Agent 用自然语言描述需求即可检索并加载。

层次化匹配与降级：高效匹配的关键在于工具组织本身具有层次结构。
