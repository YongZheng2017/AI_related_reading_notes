# 上下文工程

上下文工程（Context Engineering）：上下文的设计和管理。

&nbsp;

## 上下文：决定 Agent 能力上限的关键

对远程工作友好的团队往往也对 AI Agent 友好。信息是公开的、可检索的、结构化的。
Agent 的下一步行动取决于截至当前的完整交互上下文，而不只是眼前这一条输入。 

Agent 如何调用大模型：理解 API 的上下文结构

&nbsp;
消息的四种角色：

1. system：系统提示词。由开发者编写，定义 Agent 的身份、行为规则、约束条件。

2. user：用户消息。

3. assistant：助手消息。模型之前的回复，包括文本回复和工具调用请求。

4. tool：工具结果。 Agent 框架执行工具后，将结果以 tool 角色的消息送回给模型。

&nbsp;

大模型 API 最基本的交互模式——每次调用都是无状态的，所有模型需要的信息必须在请求的消息列表中完整提供。
消息示例：

```
// ═══ Request constructed by the Agent framework ═══
{
    "model": "Qwen3-0.6B",
    "messages": [{
            "role": "system", // ← Written by developer
            "content": "You are a helpful coding assistant. Follow user instructions."
        },
        {
            "role": "user", // ← User input
            "content": "Hello, who are you?"
        }
    ]
}

// ═══ Response returned by the API ═══
{
    "choices": [{
        "message": {
            "role": "assistant", // ← Generated by model
            "content": "Hi! I'm a coding assistant. I can help you write code, debug issues, and↪
            explain technical concepts.How can I help ? "
        }
    }]
}
```

&nbsp;

带工具调用时，模型只发出调用请求，真正执行工具的是 Agent 框架。这是理解 Agent 架构的关键：模型负责决策（调用什么工具、传什么参数）， Agent 框架负责执行（实际调用
API、运行代码）。
Agent 框架拿到模型的工具调用请求后，实际执行工具（比如调用时间 API 和天气 API），然后将完整的对话历史加上工具执行结果一起发送给模型发起下一次API请求。
三个关键细节：

1. 第二次请求包含了第一次的全部对话历史——system 消息、 user 消息、第一次的 assistant 回复（包含工具调用），以及新增的 tool 结果。

2. 第一次的 assistant 消息被原样放回消息列表

3. tool 消息通过 tool_call_id 与对应的工具调用关联

ReAct循环：“请求 → 工具调用 → 执行 → 送回结果 → 再请求”

while True:

    # Execute each tool requested by the model, append results to message list
    for tool_call in assistant_message.tool_calls:
        result = execute_tool(tool_call.function.name, tool_call.function.arguments)
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": result,
        })
    # Return to top of loop, call model again with updated message list

## KV Cache 友好的上下文设计

KV Cache （缓存命中）的做法是：把前一轮的中间计
算结果缓存下来，下一轮只需要计算新增 token 的部分。 前提是要复用的上下文 token 前缀保持不变。

三条核心结论：

1. 系统提示词和工具定义一旦确定就不要改；

2. 动态信息永远追加到末尾；

3. 使用标准 API 格式，不要自行拼接消息。

&nbsp;

注意力机制：注意力机制通过三个向量来“注意”问题的重点。

1. Query（查询）：当前词发出的“搜索请求”

2. Key（键）：每个词的“标签”，用于被搜索匹配

3. Value（值）：每个词的“内容”，匹配成功后被提取

&nbsp;

计算过程：

1. 首先，生成 Query 向量（一串数字，代表“我在找什么”）；

2. 然后，Query 与每个词的 Key 做点积（可以理解为“匹配度打分”——两组数字逐位相乘再加起来，结果越大说明越匹配），得到注意力权重；

3. 最后，用这些权重对所有词的 Value 加权求和——打分高的词贡献多，打分低的词贡献少，就像考试按权重算总分一样，最终合成出一个综合理解。

KV Cache 就是把已算过的 K 和 V 缓存起来，让新词直接复用。

&nbsp;

注意力的几个关键模式：

1. 注意力储存池：序列的第一个 token 往往吸收了异常高的注意力权重，有时超过总注意力的 70%。

2. 思考的三角形模式：模型思维链（<think> 标签内）展现出三角形状的自注意力模式——生成新的思考内容时频繁“回看”之前的思考内容和工具定义。

3. 输出的三角形模式：思考结束后的输出过程展现出另一个三角形，模型用思考过程作为提示来输出回答。

4. 位置偏好（Position Bias） ：模型对上下文开头和结尾的信息分配了更高的注意力，中间部分则更容易被忽视。因此，在设计上下文时，把最关键的信息放在开头或结尾是一项重要的实践原则。

&nbsp;

Chat Template：

- 负责将API 层面的结构化消息转换为模型能理解的线性 token 流；
- 不同的模型家族（Qwen、 Llama、 Gemma）使用不同的格式；

示例

```
<|im_start|> system
你是助手 <|im_end|>
<|im_start|> user
你好 <|im_end|>
<|im_start|> assistant
```

&nbsp;

常见的错误上下文管理模式：

- 动态系统提示词
- 动态用户配置
- 工具定义的动态排序
- 滑动窗口（Sliding Window）对话历史：会破坏上下文的前缀一致性；可能丢失关键的工具调用结果。
- 文本格式化方法：偏离了模型训练时使用的标准消息格
  式从而导致各种问题。模型提供商为标准接口做
  了大量的优化，偏离标准格式往往是在给自己挖坑。

&nbsp;

KV Cache：模型内部的机制——在一次推理过程中，缓存已计算的 token 的键值对，避免重复计算。 
Prompt Cache：推理引擎的优化——在多次 API 请求之间缓存相同前缀的计算结果。
两者的优化原理相似（都利用前缀不变性），但作用层级不同： KV Cache 加速单次请求内的 token生成， Prompt Cache 减少跨请求的重复计算成本。

&nbsp;

缓存作为架构约束：在设计 Agent 架构时，缓存经济性不是事后优化，而是前置约束。

- 提示词的结构由缓存边界决定。提示词的排列顺序首先由缓存的经济性决定，其次才是语义逻辑。
- 子 Agent 必须与父 Agent 字节级对齐。当主 Agent 派生子 Agent 或进行旁路查询时，如果子 Agent 继承父Agent 的上下文，子 Agent 的提示词、工具定义、模型配置、消息前缀和思考配置必须与父 Agent 逐字节匹配。
- 工具结果的替换字符串在首次出现时就被冻结。

## 提示工程

提示工程（Prompt Engineering）的核心对象是系统提示词（System Prompt），是 Agent 的“员工手册”，定义了 Agent 的身份、行为规则、约束条件和工作流程。

系统提示词的设计有一个实用的检验标准： 如果一个聪明的新员工读完你的系统提示词还不知道该怎么做，Agent 也一样不知道。

&nbsp;

如何优化系统提示词：

1. 语气与风格：系统提示词的“人格”

2. 结构化提示：系统提示词的“格式”

3. 流程驱动 vs 规则堆砌：系统提示词的“组织方式”
   a. 流程驱动的提示词就像一份优秀的新员工培训手册，提供了清晰的标准操作流程（SOP）

4. 业务规则细化：系统提示词的“内容”
   a. 必须将决策规则明确到可执行的程度。
   b. 提示词一般由产品经理设计，基于线上数据分析、用户反馈和运营经验来迭代优化规则定义。

5. Few-shot 示例：何时给模型看例子
   a. 模型从示例中“临时学会”模式，其效果往往胜过等量篇幅的抽象规则；
   b. 工程上有两个决策点。第一， 示例放在哪里：放在系统提示词中，示例成为静态前缀的一部分，对所有请求生效；也可以伪造一组 user/assistant 消息放在首轮对话中，适合按会话类型选用不同示例集的场景。第二， 示例对KV Cache 前缀稳定性的影响：一旦确定就应当保持字节级稳定。

6. 工具定义的设计
   a. 精心设计使用边界（“NEVER invoke grep or rgas a Bash command”）、具体示例（timezone: 'America/New_York'）、性能提示（“Batch your tool calls together”）
   以及工具间的协作关系（“Use the Read tool at least once before editing”）。
   b. 工具定义本身也在向Skills式的“渐进式披露”演进，且已经是 API 层的原生能力而非框架补丁。渐进式披露思路：静态前缀里只保留工具的名称和简述，完整 schema 在模型按需请求后追加到上下文末尾

7. 提示注入：上下文安全的核心威胁
   a. 提示注入（Prompt Injection）是 Agent 安全的核心威胁之一。其本质是：攻击者通过Agent 处理的外部内容（网页、邮件、文档等），将伪装成系统指令的文本混入上下文，从而劫持 Agent 的行为。
   b. 每一个感知工具——网页阅读、文档解析、邮件处理——都是潜在的注入入口。
   c. 核心是帮模型分清“指令”与“数据”——让它知道哪些内容有权指挥自己，哪些内容只是
   待处理的素材；
   d. 提示注入的防御方法：
       i. 来源标记：在外部内容注入上下文之前，用明确的标记包裹并标注来源；
       ii. 结构化角色：严格利用 Chat Template 的角色体系（system/user/assistant/tool）传递信息，让模型依据训练时建立的优先级区分可信指令与外部数据；
       iii. 输入清洗：过滤外部内容中的可疑模式（如“忽略之前的指令”等常见注入短语）。
   e. 安装来源不明的 Skill
   之前必须审查其内容，如同审查将要执行的代码。 
   f. 上下文层的防御（来源标记、指令与数据分离、输入清洗）只是第一道防线，它只能降低攻击成功率，无法做到万无一失。还需要注意执行层的防御——权限控制、沙盒隔离、对高风险操作的独立审查、检索内容带来的注入风险（知识库中被投毒的文档同样是注入通道）等。

## 动态提示词与 Agent Skills

Skills：领域能力的可组合单元。核心思想是将 Agent 的能力模块化为独立的、可按需加载的知识包，每个 Skill 本质上是一套包含专业领域指导的提示词集合。

Skills 采用了渐进式披露（Progressive Disclosure）的设计哲学——先给 Agent 看一份目录摘要，需要时再加载完整内容。

- 第一层（元数据）：每个 Skill 必须包含一个 SKILL.md 文件，开头是 YAML frontmatter，包含 name 和 description 两个字段。数据中的description 字段是路由决策的关键——它应当足够短（控制常驻的 token 量），但写法要像路由条件而非功能介绍。可以明确写出“何时使用”和“何时不使用”的边界，并给出几条典型反例。
- 第二层（核心流程） ：当 Agent 判断某个任务需要特定的 Skill 时，运行时才加载完整的 SKILL.md。
- 第三层（细则）：通过文件引用深入到更详细的子文档。 

&nbsp;

如何编写一份可用的 Skill：

1. 角色与读者说明这份 Skill 服务谁、面向什么任务，以及输出应达到什么标准；

2. 核心原则只保留三到五条最重要的判断，并为关键原则配正例和反例；

3. 禁止清单记录高频错误、越权动作和容易误解的表达，同时写清合法例外；

4. 参考资料放术语表、模板、范文和更详细的子文档。规则应尽量写成“作用域 + 动作 + 例外 + 验证方式”，避免把所有可能的情况堆成一张越来越长的禁用词表。

## Agent 状态栏：通过元信息增强 Agent 轨迹管理

Agent状态栏（Agent Status Bar）：Agent 框架把任务进度、环境变化和工具调用计数等动态信息整理成结构化摘要并注入上下文的机制。是 Agent 框架在上下
文末尾持续注入的状态摘要。

理论基础：上下文学习更像检索而非推理——模型擅长从已有内容中查找信息，但不擅长主动归纳和总结。

本质是把分散在上下文各处的隐式状态提炼为可直接使用的显式知识。

&nbsp;

Agent 状态栏的构成：

- 任务规划：可以引入 TODO 列表，将任务分解为清晰的步骤。
- 事件的侧信道信息（Side-channel Information）：为每个事件附加元数据——精确的时间、地理位置、距上次Agent 回复的时间间隔等。
- 环境当前状态的观察摘要：包括动态的环境信息（系统时间、工作目录等）、异常操作提醒（“该工具已被重复调用 N 次”）、以及从隐式状态到显式观察的转换。

&nbsp;

一个重要的实现细节是： Agent 状态栏在 API 层面实际上是作为一条 user 角色的消息插入到上下文末尾的——而不是修改开头的 system 消息。借用 user 角色这个消息槽位，向模型注入由 Agent 框架自动生成的系统状态信息。

&nbsp;

状态更新的两种实现：

- 实现一：每轮替换。每次 API 调用前，从消息列表中移除上一轮的状态消息，在末尾追加最新状态。移除旧状态会使其位置之后的所有缓存失效。
- 实现二：持久追加。状态消息一旦注入就永久留在轨迹中，每轮只在末尾追加新的状态。 这种方式对缓存完全友好。

状态很小、两次更新间产生的消息很多，且会话长度受控时，选择实现二；状态较大、更新频繁或轨迹很长时，选择实现一。

## 上下文压缩策略

为什么需要压缩：

1. 第一，解决长度约束和成本约束。上下文窗口有限；token 越多， API 成本越高，推理延迟也会急剧上升。

2. 第二，提升思考质量。总结后的知识比原始形式更利于模型使用。

3. 第三，缓解模型的上下文焦虑（Context Anxiety）。当模型认为上下文窗口即将耗尽时，可能在任务尚未完成前提前收尾。

注意力机制擅长在已有内容里“查找”，却不擅长在一次前向传播里主动“归纳统计”。上下文压缩把需要思考才能得到的结论，变成可以直接检索的知识。
上下文腐化（Context Rot）：长上下文会导致检索精度的下降。明明上下文窗口还远没有满，但 Agent 突然找不到关键信息了，或者反复纠结于一个早已解决的问题。
上下文压缩的设计原则：与其期望模型从冗长的上下文中自动学习，不如主动地、显式地进行知识提炼。不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识。

&nbsp;

压缩不是在单次 API 调用的过程中修改上下文，而是在两次 API 调用之间，由 Agent 框架对消息列表进行预处理。

&nbsp;

生产级的分层压缩机制：

1. 工具结果预算控制

2. 噪声直接删除

3. API 层微压缩

4. 归档式摘要

5. 全量压缩

&nbsp;

压缩策略的设计原则

1. 信息价值的非均匀分布：：关键的决策点（如人员名单）的价值高于支撑性的证据（如新闻细节），更高于冗余的噪声。

2. 语义完整性：不可丢失关键信息。

3. 任务相关性：检索类任务要保留广度，分析类任务要保留深度，创作类任务要保留灵感触发点；理想的 Agent 应能按任务类型自适应地选择压缩策略。

4. 压缩即理解：有效的压缩需要深层的语义理解。

压缩最容易丢失的是早期的架构决策、约束背后的理由和失败的路径。因此， Agent 需要定期将进展记录到文档中，而不是把所有信息零散地放在Agent 执行历史中。

&nbsp;

隔离优于压缩：让大体积的中间信息根本不进入主上下文。这就是子 Agent 上下文隔离——主 Agent 把“在代码库中大范围搜索”这类会产生海量中间内容的任务，委派给一个独立的子 Agent；子 Agent 在自己的上下文中完成探索，只把几百 token 的结论性摘要回传给主 Agent。
